AIU 0.3.3 stops the repeated macOS Keychain prompts for Claude Code's login.

AIU now reads and writes Claude Code's `Claude Code-credentials` Keychain item through `/usr/bin/security`, exactly as Claude Code does. Earlier releases used Security.framework, which made AIU a second signer on that item, so approving one tool could leave the other asking again and "Always Allow" did not stick. If an older release left the item trusting only AIU, macOS may ask once more when `security` next reads it; after you choose Always Allow, both tools share that approval.

The menu bar app adds a Keychain Access window. At launch, and under Settings → Keychain access, it checks without prompting whether macOS would ask about Claude Code's login or AIU's own accounts, including older per-account items that still need to migrate. Allow then triggers the macOS prompt on purpose, with a reminder to choose Always Allow. The same check is available as `aiu keychain`, and `aiu keychain allow claude|aiu` triggers the prompt from the terminal.

AIU also follows `CLAUDE_SECURESTORAGE_CONFIG_DIR` when locating Claude Code's login, reads a CLI's login only when one of that provider's accounts is shown, and takes Claude Code's OAuth refresh lock when refreshing the token Claude Code holds, so the two no longer spend the same single-use token.

The Homebrew bottle is signed with Parable's Developer ID Application certificate. Source builds may use an ad hoc signature when the signing certificate is unavailable; the bottle is not notarized.
